## Технічні рішення / Контекст

### Діагноз (з аналізу коду 2026-08-09)

1. **`LoadPrices()` читає ВЕСЬ регістр цін** — вся історія `ЦеныНоменклатуры` вивантажується в пам'ять, відбір останнього запису робиться в .NET. **Рішення: підзапит (subquery)** — регістр фільтрується WHERE-клаузою каталогу прямо в запиті 1С.
2. **COM round-trip на кожен рядок** — `GetRefGuid()` викликає `УникальныйИдентификатор` через `InvokeMember` для кожного посилання в кожному рядку. Один і той же товар/тип ціни зустрічається в багатьох рядках — GUID витягується повторно. Те саме з `GetRefName()` для одиниць виміру. **Рішення: `ConditionalWeakTable` кеш.**
3. **`BuildStock()` — квадратична складність O(n×m)** — для кожного товару лінійний пошук по всьому списку залишків. **Рішення: `Dictionary` за `ItemGuid`.**
4. **`BuildPrices()`** — лінійний пошук по `priceTypes` для кожного товару. **Рішення: `Dictionary` за GUID типу.**

### Випробувані підходи, що не спрацювали

- **`СрезПоследних()`** через dynamic → COM access violation `0xC0000005` (падіння процесу).
- **GUID-літерали `&{guid}`** в `IN (...)` та `OR`-умовах → синтаксична помилка 1С (символ `&` зарезервований для параметрів запиту).
- **Рішення, що спрацювало:** підзапит `WHERE Цены.Номенклатура IN (SELECT ... FROM Справочник.Номенклатура ... WHERE ...)` — фільтрація на боці 1С.

### Подальше покращення (для великих наборів)

Для наборів у тисячі товарів підзапит може стати вузьким місцем. Рекомендований підхід (з `com-tips.md` / `Failed_to_read_catalog.md`):
- Створити `Массив` 1С через `connection.NewObject("Массив")`
- Конвертувати GUID → COM-посилання через `УникальныйИдентификатор` + `ПолучитьСсылку`, додати в масив
- Передати масив як параметр: `query.SetParameter("ItemsArray", v8Array)` + `В (&ItemsArray)`
- 1С оптимізує `В (&Массив)` в один ефективний `IN (...)` з використанням індексів
- При >500-1000 елементів — розбивати на пакети (batching)
